Every RAG demo looks great until someone asks it a question you didn't test. A golden set is how you stop finding that out in production: a small hand-built set of questions over your own corpus, three numbers per answer, and a clear read on whether your retriever or your generator is the one lying to you. This page builds one end to end on a real (if small) documentation corpus — including the failure case that eyeballing chat logs always misses: an answer that sounds completely confident and is quietly wrong.

If you haven't read [Evaluating RAG Quality](/learn/rag/evaluating-rag-quality) yet, go there first for what context recall, faithfulness, and answer relevance actually mean and why those three in particular. This page assumes you know the definitions and shows you the part nobody puts in the slide deck: how to actually build the harness, by hand, on a corpus small enough to reason about.

## The setup

You're evaluating the retrieval layer behind an internal support bot for **Ledgerly**, a fictional expense-reporting SaaS product — fictional so the numbers below are yours to check, not a benchmark to take on faith. The corpus is its internal docs wiki: 12 markdown pages, chunked into roughly 70-token-to-300-token pieces.

| Doc | Topic | Chunks |
|---|---|---|
| `billing-and-plans.md` | Pricing tiers, seats, billing cycles | 5 |
| `expense-categories.md` | Category taxonomy, custom categories | 6 |
| `receipt-ocr-limits.md` | File types, size limits, OCR confidence | 4 |
| `approval-workflows.md` | Approval chains, notifications, escalation | 8 |
| `sso-and-scim.md` | SAML/SCIM setup, provisioning | 7 |
| `api-rate-limits.md` | Rate limits per plan, burst behavior | 5 |
| `data-retention.md` | Retention windows by plan and data type | 6 |
| `refunds-and-cancellations.md` | Cancellation flow, refund eligibility | 4 |
| `mobile-app-offline-mode.md` | Offline queueing, sync behavior | 5 |
| `integrations-quickbooks.md` | Sync mapping, conflict resolution | 9 |
| `audit-log-export.md` | Export formats, retention, access control | 6 |
| `multi-currency-support.md` | Supported currencies, FX timing | 8 |

That's 73 chunks total — small enough that you, a human, could in principle read the whole corpus in twenty minutes. That's not incidental. A golden set only works if someone who understands the source material writes it, and that's only realistic on a corpus this size or on a well-scoped slice of a bigger one.

The pipeline itself is nothing exotic: embed the chunks, top-k=5 vector retrieval, a general-purpose instruction-tuned model for generation. The point of this exercise isn't the pipeline — it's the harness around it.

## Step by step

### 1. Freeze the corpus

Copy the 12 docs, chunk them, and don't touch them again until the eval is done. Note the embedding model and chunking parameters (chunk size, overlap, splitter) next to the golden set file.

> **Why this step?** Every score you compute is a score *for this corpus and this chunking*. If someone edits `refunds-and-cancellations.md` next Tuesday, your context recall numbers are now measuring a corpus that no longer exists. This is also where [chunking strategy](/learn/rag/chunking-strategies-for-documents) quietly decides your ceiling: if a chunk boundary splits the sentence containing the answer, no retriever will ever hit 1.0 recall on that question, and you want to know that's a chunking problem before you go tune the retriever for a week.

### 2. Write ~20 questions by hand

Not generated by an LLM reading the docs — written by you, reading the docs. Aim for a spread of failure-prone types, not uniform coverage:

- **Single-hop factual** (answer lives in one chunk) — the easy case, but you need a floor.
- **Multi-hop** (answer requires combining two chunks, possibly from two docs).
- **Numeric/precise** (a specific number a model might "round" from memory instead of reading).
- **Unanswerable** (not in the corpus at all — tests whether the system says so instead of inventing an answer).
- **Comparison** (differs between two plans, two states, two docs).

```python
golden_set = [
    {
        "id": "g01", "type": "single-hop",
        "question": "What's the maximum file size for a receipt photo uploaded through OCR?",
        "gold_chunks": ["receipt-ocr-limits.md#c1"],
        "gold_answer": "10 MB per image; larger files are rejected before OCR runs.",
    },
    {
        "id": "g02", "type": "multi-hop",
        "question": "If a manager rejects an expense report submitted from the mobile app while the phone was offline, when does the employee find out?",
        "gold_chunks": ["approval-workflows.md#c3", "mobile-app-offline-mode.md#c2"],
        "gold_answer": "Within 5 minutes of the rejection being recorded — but the approval clock doesn't start until the offline report finishes syncing.",
    },
    {
        "id": "g03", "type": "single-hop, numeric",
        "question": "How many days do I have to request a refund after cancelling?",
        "gold_chunks": ["refunds-and-cancellations.md#c2"],
        "gold_answer": "14 days from the cancellation date, and only for the unused portion of the current billing cycle.",
    },
    {
        "id": "g04", "type": "unanswerable",
        "question": "Does Ledgerly support filing expenses in cryptocurrency?",
        "gold_chunks": [],
        "gold_answer": "Not documented — correct behavior is to say so, not guess.",
    },
    {
        "id": "g05", "type": "multi-hop, comparison",
        "question": "What happens to my audit logs if I downgrade from Business to Starter?",
        "gold_chunks": ["data-retention.md#c4", "audit-log-export.md#c1"],
        "gold_answer": "Logs older than 30 days are purged on downgrade — export them first.",
    },
    # g06–g20 follow the same shape: 3 more unanswerable, 5 more
    # single-hop numeric lookups, 6 more multi-hop, 4 comparisons —
    # drawn from the remaining seven docs.
]
```

> **Why this step?** Twenty questions you understand beat two hundred an LLM generated by paraphrasing the docs back at you. One trap to watch for as you write them: if your question echoes the source chunk's exact wording ("what is the maximum file size for OCR uploads" lifted almost verbatim from the doc), retrieval will look artificially strong — real users don't type in doc-speak. After drafting each question, rewrite it in plainer or differently-worded phrasing before it goes in the set.

### 3. Record the gold chunks and gold answer per question

This is already visible in the `golden_set` above — `gold_chunks` is what a correct retrieval *must* include; `gold_answer` is what a correct generation should say. Writing these down is the actual expensive part of building a golden set; running the pipeline against it is cheap and repeatable.

### 4. Run the pipeline once, save everything

For each question, run retrieval and generation, and store the retrieved chunk IDs and the generated answer text alongside the golden row. Don't recompute this per metric — score all three metrics off the same saved run, so they're describing the same answer.

### 5. Score context recall

```python
def context_recall(gold_chunks: list[str], retrieved_chunks: list[str]) -> float:
    """Fraction of the chunks you hand-labeled as necessary that the
    retriever actually returned. Defined only for answerable questions —
    score unanswerable ones separately (step 8)."""
    if not gold_chunks:
        return None
    hit = len(set(gold_chunks) & set(retrieved_chunks))
    return hit / len(gold_chunks)

# g02: retriever came back with approval-workflows.md#c3 but missed
# the offline-sync chunk entirely
context_recall(
    gold_chunks=["approval-workflows.md#c3", "mobile-app-offline-mode.md#c2"],
    retrieved_chunks=["approval-workflows.md#c3", "approval-workflows.md#c1", "billing-and-plans.md#c4"],
)
# -> 0.5
```

> **Why this step?** Set-overlap recall is a blunt instrument compared to what tools like RAGAS do (LLM-based sentence attribution against the retrieved text), but it's the honest v0: you already hand-labeled the required chunks in step 3, so this is nearly free, and it tells you the one thing that matters before you look at the answer at all — did the generator even have a chance?

### 6. Score faithfulness

```python
def faithfulness(answer: str, context: str, judge) -> float:
    """judge is any callable(prompt) -> str, e.g. a wrapped LLM call."""
    claims = judge(
        f"List the factual claims in this answer as short standalone "
        f"sentences, one per line:\n\n{answer}"
    ).splitlines()
    if not claims:
        return 1.0
    verdicts = [
        judge(
            f"Context:\n{context}\n\nClaim: {claim}\n\n"
            "Does the context support this claim? Answer only 'yes' or 'no'."
        ).strip().lower()
        for claim in claims
    ]
    return sum(v == "yes" for v in verdicts) / len(verdicts)
```

Faithfulness (sometimes called groundedness) decomposes the answer into individual claims and checks each one against the retrieved context — not against the internet, not against the gold answer, only against what the model actually had in front of it.

### 7. Score answer relevance

```python
import numpy as np

def cosine_similarity(a, b):
    a, b = np.array(a), np.array(b)
    return a @ b / (np.linalg.norm(a) * np.linalg.norm(b))

def answer_relevance(question: str, answer: str, embed) -> float:
    return cosine_similarity(embed(question), embed(answer))
```

This is the simplest version — a direct [cosine similarity](/learn/maths-foundations/cosine-similarity-angular-distance-embedding-retrieval) between question and answer embeddings. RAGAS's actual method is more robust (generate several synthetic questions *from* the answer, embed those, and average their similarity to the real question) because it's less fooled by an answer that repeats question vocabulary without saying much. Start with the direct version; upgrade once you trust the harness.

### 8. Read the three numbers together, per question

This is the step people skip, and it's the one that actually separates retrieval failures from generation failures. Do it per question, not on the averages:

| Context recall | Faithfulness | Answer relevance | Diagnosis |
|---|---|---|---|
| Low | — | — | **Retrieval failure.** The generator never had the material. Fix chunking or retrieval — a prompt change can't help here. |
| High | Low | — | **Generation failure.** The context was there and the model didn't use it right. Fix the prompt or decoding, not the retriever. |
| High | High | Low | **Generation failure**, different flavor: grounded but off-target — answering an adjacent question, or too verbose to land. Fix instruction-following. |
| High | High | High | Working as intended for this question. |

g02 (the offline-mobile question) lands in row one: recall 0.5, and whatever faithfulness/relevance come out to don't matter yet — the fix is retrieval, likely [parent-document retrieval](/learn/rag/parent-document-retrieval) or a rewrite that helps the retriever bridge two docs, not a prompt tweak.

g03 (the refund question) lands in row two, and that's worth walking in full.

## Where it breaks

g03's retriever did its job — recall is 1.0. Here's the chunk it correctly pulled back:

> Cancellation and refunds: You can cancel your Ledgerly subscription at any time from Settings > Billing. Refund requests must be submitted within 14 days of the cancellation date and apply only to the unused portion of the current billing cycle. Annual plans are prorated to the month; monthly plans are not eligible for partial-month refunds.

And here's what the model generated from it:

> "You have 30 days after cancelling to request a refund. Once approved, you'll receive a prorated refund to your original payment method within 5–7 business days."

Read that answer cold and it's fine — fluent, specific, confidently on-topic. Nothing about it *looks* wrong. That's exactly the case a golden set exists to catch.

Run it through the three metrics:

- **Context recall: 1.0.** The chunk with the real answer was retrieved. Retrieval is not the problem, and no amount of reranking or hybrid search will fix what's about to go wrong.
- **Answer relevance: high (≈0.85 by direct cosine).** The answer is unmistakably *about* refund timing — same topic, same shape of question. Relevance has no access to the context or the gold answer; it only checks that the answer addresses the question asked. A wrong number about the right topic still scores well here.
- **Faithfulness: 0.0.** Decompose the answer into its two claims and check each against the retrieved chunk: "the refund window is 30 days" is directly contradicted (the chunk says 14), and "refunds go to the original payment method within 5–7 business days" doesn't appear anywhere in the context — not contradicted, just fabricated. Zero of two claims supported.

Faithfulness is the only one of the three that catches this, because it's the only one that checks the answer's claims against what was actually retrieved, claim by claim. Context recall checks the retriever, not the answer. Answer relevance checks the answer against the question, not against the source. A model that ignores its context and answers fluently from its training-data prior will sail through both of those and get caught by exactly one metric — which is the whole argument for scoring all three instead of picking a favorite.

**The fix** is a generation constraint, not a retrieval one:

```
Answer only using the provided context. If the context does not
contain the answer, say you don't have that information rather
than filling it in from general knowledge.
```

Re-run g03 with that instruction in place and the model now produces something closer to: "Refund requests must be submitted within 14 days of the cancellation date, and only for the unused portion of your current billing cycle." One claim, directly supported — faithfulness 1.0. It also drops the payment-method detail entirely, because that detail was never in the context and now has nowhere to hide. If you want that discipline enforced structurally rather than by prompt instruction alone, pair this with [inline citations](/learn/rag/grounding-answers-with-citations) — a claim with no citation to point to becomes a claim you can reject automatically, before a human ever reads it.

## Takeaways

- Twenty hand-written questions on a corpus you actually read beat two hundred auto-generated ones — you know what "correct" means for each, which is the part that's expensive to get from a model.
- Score per question before you average anything. An aggregate faithfulness of 0.9 across twenty questions hides the one answer that's confidently, fluently wrong.
- The three metrics aren't redundant, they're triangulating: context recall checks the retriever, faithfulness checks the generator against what it was handed, answer relevance checks the generator against what was asked. A failure isolated to exactly one of them tells you exactly one component to go fix.
- Twenty questions is enough to catch the two or three failure modes that actually recur in a corpus this size — it is not enough to certify a launch. Grow the set as you find new failure types, and once you're gating deploys on these numbers, aim for well beyond twenty.
