A native PDF — one exported from Word, or generated by an accounting system — has text embedded in it, and getting that text out is close to trivial. A scanned document has none. It is a photograph of paper, and every enterprise deployment in India will hand you a folder of them: a GST invoice photographed on a phone by a small vendor with no billing software, a discharge summary typed in English with a doctor's handwritten note in the margin, a government scheme application scanned at a district office on a shared machine that has not been cleaned in years. Treat these as a different problem from PDF parsing, because they are one.

## Why this problem is bigger in Indian enterprise accounts

Three things compound here in a way that a US or EU deployment usually does not see at the same scale. Vendor invoicing outside large enterprises is still frequently paper-first, so a mid-size manufacturer's accounts-payable folder is a mix of native PDFs from big suppliers and phone-camera scans from small ones. Documents are routinely mixed-script: an invoice header in English, a product description in Hindi, a Tamil or Telugu stamp from a regional office, sometimes on the same page. And scan quality is uneven — a flatbed scanner in a metro headquarters producing a clean 300dpi image, and a branch office three states away sending a photo taken at an angle under a tube light.

None of this is a reason to avoid the problem. It is a reason to design the pipeline assuming variable input quality from day one, rather than discovering it in week three when the accuracy numbers from your test batch do not hold on the real corpus.

## The pipeline, in order

**1. Preprocess the image before OCR sees it.** Deskew (correct the rotation), binarise or enhance contrast, and denoise. A scan photographed at a slight angle can drop OCR accuracy sharply on the affected lines even when a human reads it without difficulty.

```python
import cv2
import numpy as np

def deskew(image_path: str, out_path: str) -> float:
    """Deskew a scanned document image and return the correction angle in degrees."""
    img = cv2.imread(image_path, cv2.IMREAD_GRAYSCALE)
    thresh = cv2.threshold(img, 0, 255, cv2.THRESH_BINARY_INV | cv2.THRESH_OTSU)[1]
    coords = np.column_stack(np.where(thresh > 0))
    angle = cv2.minAreaRect(coords)[-1]
    angle = -(90 + angle) if angle < -45 else -angle
    (h, w) = img.shape
    matrix = cv2.getRotationMatrix2D((w // 2, h // 2), angle, 1.0)
    rotated = cv2.warpAffine(img, matrix, (w, h), flags=cv2.INTER_CUBIC,
                              borderMode=cv2.BORDER_REPLICATE)
    cv2.imwrite(out_path, rotated)
    return angle
```

**2. Choose the OCR engine on the actual document mix, not a default.** Tesseract, open-source and free, handles Devanagari, Tamil, Telugu, and most Indian scripts with the right trained language packs (`tesseract --list-langs` to check what is installed, `hin+eng` as the language argument for a mixed Hindi-English page), and it runs entirely inside the customer's environment, which matters the moment the documents are financial or medical and cannot leave the perimeter. Cloud OCR APIs (from the major cloud vendors) generally score higher on accuracy for difficult scans and layout-heavy documents like tables, at the cost of the document leaving the network, a per-page charge, and a residency conversation you need to have before the first document is sent — see the residency lesson in this module. Plan for both being on the table, and let the deployment's constraints, not a preference, decide.

**3. Run OCR and keep the confidence score, not just the text.** Both Tesseract and the cloud engines report a confidence per word or per line. Throwing this away is the single biggest mistake in a first OCR pipeline, because it is the only signal you have for which extractions to trust.

```python
import pytesseract
from pytesseract import Output

def ocr_with_confidence(image_path: str, lang: str = "hin+eng"):
    """Run OCR and return (full_text, mean_confidence, low_confidence_words)."""
    data = pytesseract.image_to_data(image_path, lang=lang, output_type=Output.DICT)
    words, confidences, low_conf = [], [], []
    for text, conf in zip(data["text"], data["conf"]):
        conf = int(conf)
        if text.strip() and conf >= 0:            # -1 means no text detected in that box
            words.append(text)
            confidences.append(conf)
            if conf < 60:
                low_conf.append((text, conf))
    mean_conf = sum(confidences) / len(confidences) if confidences else 0.0
    return " ".join(words), mean_conf, low_conf
```

**4. Extract structured fields, not just raw text.** For a semi-structured document like an invoice, run raw OCR text through a small set of targeted extractors: a regex for a GSTIN (a fixed 15-character format), a regex or a labelled-field lookup for an invoice number, and a date parser tolerant of the three or four date formats that show up across vendors. Where the layout is regular enough (a template the vendor reuses), a table/layout-detection step before OCR — cropping to known regions — beats running OCR over the whole page and hoping a downstream parser finds the amount in a wall of text.

**5. Score each extracted field, and route low-confidence fields to a human queue.** This is the step that makes the pipeline trustworthy rather than merely functional.

```python
import re

GSTIN_RE = re.compile(r"\b\d{2}[A-Z]{5}\d{4}[A-Z]\d[A-Z]\d\b")

def extract_fields(text: str, mean_conf: float):
    gstin_match = GSTIN_RE.search(text.replace(" ", ""))
    fields = {
        "gstin": {"value": gstin_match.group() if gstin_match else None,
                   "confidence": mean_conf if gstin_match else 0.0},
    }
    needs_review = [name for name, f in fields.items()
                     if f["value"] is None or f["confidence"] < 70]
    return fields, needs_review
```

A document with every field above threshold moves straight to the downstream system. A document with any field below it goes to a review queue with the original image, the extracted value, and the confidence, so a human corrects one field in seconds rather than re-keying the whole document. In a well-tuned pipeline over a mixed real corpus, this queue typically holds a meaningful minority of documents, not zero and not most; if it is empty, your threshold is too permissive, and if it is most of the corpus, your OCR engine or preprocessing is wrong for this document set.

## The mixed-script trap specifically

A page with English headers and Hindi body text needs the multi-language model invoked correctly (`hin+eng`, not `hin` or `eng` alone), and even then, expect materially lower accuracy on the Hindi portions than the English ones, because font quality and stamp/handwriting overlap concentrate there. Do not average a mixed-script document's confidence into one number and threshold on that; score the English fields (often the ones you need structurally — amounts, dates, GSTINs) and the vernacular fields (often names, addresses, descriptions) separately, because they will need different thresholds and different reviewer skills.

## What you can now do

You can build an OCR pipeline that treats a scanned, mixed-script document as the normal case rather than the exception, keeps a confidence score alongside every extracted field, and routes exactly the documents that need a human to a queue instead of either trusting bad extractions or sending everything to a person. That queue, and its size over time, is also the honest metric to report to the customer: not "OCR accuracy," which nobody can verify, but "documents processed straight-through this week," which they can watch fall as the pipeline improves.
