Run `df[df["plan"] == "free"]["credits"] = 50` and pandas throws a warning, then does exactly nothing — the DataFrame is unchanged and nothing tells you that later, when you're three functions away from the line that "fixed" it. This mistake has close cousins: a slice you were sure was independent that quietly shares memory with the original, and an integer column that turns into a float the moment a single value goes missing. All of them are reproduced below, with fixes that hold regardless of which pandas you're running.

## First, check which pandas you're running

The exact warning you get for chained assignment changed in pandas 3.0, because pandas 3.0 made **Copy-on-Write (CoW)** — an opt-in feature since pandas 2.0 — mandatory and permanent. CoW changes how aggressively pandas copies data internally, and it changes the name (and occasionally the outcome) of a few things in this lesson. It does not change any of the fixes.

```python
import pandas as pd

print(pd.__version__)
print(pd.options.mode.copy_on_write)  # True on pandas 3.0+, and it can no longer be turned off
```

If `pip install pandas` today gives you 3.0.x, keep that in mind as you read: you'll see the newer error names below, not the classic ones you'll still find in five-year-old Stack Overflow answers and possibly your company's pinned `requirements.txt`.

### Chained indexing warns you — and the assignment does nothing

```python
import pandas as pd

df = pd.DataFrame({
    "user_id": [101, 102, 103, 104, 105],
    "plan": ["free", "pro", "free", "free", "pro"],
    "credits": [10, 100, 10, 10, 100],
})

# looks reasonable: give every free-plan user 50 credits
df[df["plan"] == "free"]["credits"] = 50
```

On pandas 3.0+, that line prints:

```text
ChainedAssignmentError: A value is being set on a copy of a DataFrame or Series
through chained assignment. Such chained assignment never works to update the
original DataFrame or Series, because the intermediate object on which we are
setting values always behaves as a copy (due to Copy-on-Write).

Try using '.loc[row_indexer, col_indexer] = value' instead, to perform the
assignment in a single step.
```

On pandas older than 3.0, same mistake, different wording — this is the warning the title of this lesson refers to:

```text
SettingWithCopyWarning:
A value is trying to be set on a copy of a slice from a DataFrame.
Try using .loc[row_indexer,col_indexer] = value instead
```

Either version, check the result:

```python
print(df)
#    user_id  plan  credits
# 0      101  free       10
# 1      102   pro      100
# 2      103  free       10
# 3      104  free       10
# 4      105   pro      100
```

`credits` never moved. Free-plan users still have 10.

**Why it's wrong.** `df[df["plan"] == "free"]` and `["credits"] = 50` are two separate operations, not one. The first is a `__getitem__` call that builds and returns a new object — pandas makes no promise about whether that object shares memory with `df` or is a fresh copy (and under Copy-on-Write it's unconditionally a copy). The second is a `__setitem__` call that writes `50` into *that* object. Nothing else holds a reference to it, so it gets garbage-collected right after, and the write goes nowhere. You never touched `df` — you touched a temporary built by filtering it. This is the sharp edge underneath ordinary [selecting, filtering, and indexing](/learn/python-data-apis/selecting-filtering-indexing): the moment an assignment (not a read) follows a filter, "which object did I actually just touch" stops being obvious.

**Symptom.** A warning fires at the assignment line — its exact class depends on your pandas version, but the meaning is the same — and the column you meant to update is unchanged when you inspect it afterward. In a script that doesn't print intermediate state, this ships silently: no crash, no traceback, just wrong numbers downstream.

**Fix.** Pass the row selector and the column selector into a single `.loc` call, so pandas resolves the write directly against `df` instead of against a disposable intermediate:

```python
df.loc[df["plan"] == "free", "credits"] = 50
print(df)
#    user_id  plan  credits
# 0      101  free       50
# 1      102   pro      100
# 2      103  free       50
# 3      104  free       50
# 4      105   pro      100
```

Zero warnings, and the update actually lands.

### ".loc for the rows, brackets for the column" is still chained

This one catches people who've heard "use `.loc`" without hearing the rest of the sentence:

```python
df2 = pd.DataFrame({"plan": ["free", "pro", "free"], "credits": [10, 100, 10]})

df2.loc[df2["plan"] == "free"]["credits"] = 999  # .loc is here, but it's still two calls
```

This raises the exact same warning as the mistake above and still does nothing — `credits` stays `[10, 100, 10]`.

**Why it's wrong.** `.loc[mask]` with nothing after the comma is a complete indexing operation on its own; it returns a new DataFrame the same way `df2[mask]` does. The bracket that follows is a second, separate operation chained onto that result. `.loc` only avoids the trap when both selectors — rows *and* columns — arrive in the same `[]`. "Use `.loc` somewhere in the line" isn't the rule; "resolve rows and columns in one indexing call" is.

**Symptom.** Same warning, same do-nothing result, but harder to debug because the code visibly uses `.loc` and looks like it should already be fixed.

**Fix.** Keep both selectors together: `df2.loc[df2["plan"] == "free", "credits"] = 999`.

### Mutating a slice you thought was independent — the outcome depends on your pandas version

```python
df3 = pd.DataFrame({"a": [1, 2, 3], "b": [4, 5, 6]})

col = df3["a"]      # looks like an independent Series
col.iloc[0] = 999   # no warning at all, on either pandas version
```

This is the one with zero warning either way, and it's worth running for real, because the outcome flips depending on your pandas version:

```python
print(col.tolist())   # [999, 2, 3] -- always, on every pandas version
print(df3["a"].tolist())
```

On pandas older than 3.0 (classic, Copy-on-Write off): `df3["a"]` prints `[999, 2, 3]` too — mutating `col` silently mutated `df3`.
On pandas 3.0+ (Copy-on-Write mandatory): `df3["a"]` prints `[1, 2, 3]` — `col` quietly became its own object the moment you wrote to it, and `df3` never saw the change.

**Why it's wrong.** `df3["a"]` returns a Series backed by the same underlying array as one of `df3`'s internal blocks whenever pandas can get away with it — nothing in the public API guarantees a copy. This is precisely the "returning a view versus a copy" ambiguity pandas' own documentation warns about. Classic pandas shares memory opportunistically and copies only when forced to; Copy-on-Write inverts that by copying eagerly at the point of a write, then detaching. Both are legitimate implementations of the same `df3["a"]` call, which is exactly why you can't tell from reading the code which one you're getting.

**Symptom.** No warning, on either version. The bug surfaces as data that changed somewhere you didn't touch on purpose (classic pandas) or an update that silently never reached the object you actually meant to change (Copy-on-Write) — and you only find out when you print the *other* object later.

**Fix.** Stop letting the ambiguity decide for you. If `col` is meant to be independent, say so with `.copy()`: `col = df3["a"].copy()`. If you actually meant to modify `df3`, write to `df3` directly instead of routing through an intermediate variable: `df3.loc[0, "a"] = 999`.

### Adding .copy() in the wrong place silences the warning and your update

```python
df4 = pd.DataFrame({"plan": ["free", "pro", "free"], "credits": [10, 100, 10]})

sub = df4[df4["plan"] == "free"].copy()   # no warning now
sub["credits"] = 50                        # this line is completely correct...

print(df4)     # ...but df4 never changed
#    plan  credits
# 0  free       10
# 1   pro      100
# 2  free       10
print(sub)
#    plan  credits
# 0  free       50
# 2  free       50
```

**Why it's wrong.** `.copy()` isn't a warning suppressant — it's a real instruction: "detach this object from whatever it came from." Once you call it, `sub` genuinely is independent, so assigning into it is 100% correct pandas. It's just correctly updating the wrong object. This is the single most common way people "fix" the warning after finding a Stack Overflow answer that says "just add `.copy()`": the red text disappears, they move on, and nobody checks whether `df4` itself actually changed.

**Symptom.** No warning at all. Any test that only checks "did this raise an exception" passes. The original DataFrame is silently unaffected. This is arguably worse than the chained-indexing mistake above, because the silence reads as success.

**Fix.** Decide, before you write the line, whether you want to mutate the original or produce a separate frame on purpose — they're different intents and need different code:

```python
# intent: mutate df4 itself
df4.loc[df4["plan"] == "free", "credits"] = 50

# intent: an independent frame, and df4 is deliberately left alone
sub = df4[df4["plan"] == "free"].copy()
sub["credits"] = 50  # only sub changes, and that's the point
```

Never chain a `.copy()` onto the same statement where you also mean to update the thing you filtered from.

### An integer column turns to float64 the instant a value goes missing

```python
counts = pd.DataFrame({"count": [1, 2, 3]})
print(counts["count"].dtype)   # int64

counts.loc[1, "count"] = None
print(counts["count"].dtype)   # float64
print(counts)
#    count
# 0    1.0
# 1    NaN
# 2    3.0
```

**Why it's wrong.** NumPy's `int64` is a fixed-width bit pattern with every value already spoken for — there's no bit pattern reserved for "missing." `float64` has one, `NaN`, because IEEE 754 defines it. The moment pandas needs to represent a hole in a column backed by `int64`, the only place for that hole to live is a dtype that has a `NaN`, so the whole column gets upcast to `float64`. This isn't a setting you can flip — it's a real constraint of the underlying array, the same one covered in [NumPy arrays fundamentals](/learn/python-data-apis/numpy-arrays-fundamentals). It's also not limited to direct assignment: a `.merge()` that leaves rows unmatched introduces `NaN` into any int column on the unmatched side, via ordinary [joining and merging DataFrames](/learn/python-data-apis/joining-and-merging-dataframes):

```python
left = pd.DataFrame({"id": [1, 2, 3], "name": ["a", "b", "c"]})
right = pd.DataFrame({"id": [1, 3], "score": [10, 30]})   # score is int64 here

merged = left.merge(right, on="id", how="left")
print(merged["score"].dtype)   # float64 -- even though it started as int64
```

**Symptom.** Values print as `1.0` instead of `1`, easy to miss on a quick `.head()`. It bites harder once you try to force the type back:

```python
counts["count"].astype(int)
# IntCastingNaNError: Cannot convert non-finite values (NA or inf) to integer.
# Replace or remove non-finite values or cast to an integer type
# that supports these values (e.g. 'Int64')
```

Anything downstream expecting a stable int dtype — a schema check like the ones in [validating DataFrames with schemas](/learn/python-data-apis/validating-dataframes-with-schemas), a groupby key, a join key — fails in a way that traces back to an assignment or merge several steps earlier, not to the line that actually raises.

**Fix.** If a column might ever need to represent a missing integer, opt into pandas' nullable integer dtype up front. It carries a separate missing-value mask instead of repurposing float `NaN`, so it never needs to upcast:

```python
counts = counts.astype({"count": "Int64"})   # capital I -- the nullable dtype
counts.loc[1, "count"] = None
print(counts["count"].dtype)   # Int64
print(counts)
#    count
# 0      1
# 1   <NA>
# 2      3
```

The same pattern (`"Float64"`, `"boolean"`) exists for the other dtypes that have this problem — see [handling missing values](/learn/python-data-apis/handling-missing-values) for when it's worth the switch.

### Muting the warning instead of fixing the indexing

```python
pd.options.mode.chained_assignment = None   # "fixes" the red text
```

On pandas older than 3.0, this genuinely works: set it once, and `SettingWithCopyWarning` stops appearing for the rest of the session. On pandas 3.0+, it does nothing at all — chained assignment still raises `ChainedAssignmentError` regardless of this setting, because Copy-on-Write makes the check unconditional rather than something you can opt out of.

**Why it's wrong.** Even where it still has an effect, disabling the warning doesn't resolve the underlying ambiguity of whether your write landed — it just stops pandas from telling you when it might not have. You've traded a visible signal for a silent, version-dependent maybe.

**Symptom.** Intermittent, hard-to-reproduce bugs: a column update that "usually" works and occasionally doesn't, with no warning in the logs pointing at the line that failed. On a team, this tends to surface as "the numbers were off in last week's report," with nobody able to point at a stack trace.

**Fix.** Don't disable the warning globally. Fix each call site with `.loc` (the first two mistakes above) or a correctly-placed `.copy()` (the fourth). If you're starting a new project, pick your regime deliberately: check `pd.__version__`, and on pandas 2.x, consider opting into Copy-on-Write yourself (`pd.options.mode.copy_on_write = True`) so chained-assignment behavior is deterministic now, instead of inherited later when you upgrade to 3.0.

## Pre-flight checklist

- [ ] Run `pd.__version__` and know whether you're on classic pandas or Copy-on-Write (mandatory on 3.0+, optional on 2.x) — the warning name and a couple of silent-mutation outcomes differ between them; the fixes don't.
- [ ] Never write a value through two chained `[]` / `.loc[]` calls. Row selector and column selector belong in the *same* `.loc[rows, cols] = value` call — `.loc[rows]` alone followed by `[col] = value` is still chained.
- [ ] Before mutating a variable you got by slicing a DataFrame, decide on purpose: do you want to change the original, or do you want an independent copy? Write the code for that decision — `.copy()` for independence, a direct `.loc` on the original otherwise — instead of letting pandas' internals decide for you.
- [ ] Never chain `.copy()` onto the same line you're also using to try to update the object you filtered from.
- [ ] Treat any column that might gain a missing value as a candidate for the nullable `"Int64"` / `"Float64"` / `"boolean"` dtype up front, especially before a `.merge()` or `.reindex()`.
- [ ] Never set `pd.options.mode.chained_assignment = None` as a fix for the warning — it doesn't fix anything, and on pandas 3.0+ it doesn't even suppress it.
- [ ] After any assignment you weren't fully sure about, `print()` or `.head()` the *actual* object you meant to change, not the variable you assumed was the same thing.
