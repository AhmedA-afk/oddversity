An LLM will happily process whatever you hand it and produce whatever comes out — neither side is safe by default. Guardrails are the checks you put on both ends of that pipe: before user input reaches the model, and before the model's output reaches a user or your database.

## Input guardrails

Treat user input the way you'd treat any untrusted string, then add one more concern specific to LLMs: it can try to hijack your prompt. Practical checks:

- **Length and rate limits.** Cap input size before it ever hits the model — a 50,000-token paste is a cost problem and often an abuse attempt.
- **Format checks.** If a field should be an email or a product ID, validate it with a regex before spending a model call on it.
- **Prompt injection detection.** Watch for user text that tries to override your system instructions ("ignore the above and..."). You won't catch every variant with a keyword list, but a lightweight classifier or a second cheap model call flagging suspicious patterns catches a lot of the obvious ones. See [Prompt Injection: When Content Becomes Instructions](/learn/evals-red-teaming/prompt-injection-basics) for the full threat model.
- **Delimiters.** Wrap user content in clear boundaries (XML-style tags or fenced blocks) in your prompt template so the model can tell "this is data" from "this is instructions." See [Delimiters](/learn/prompt-engineering/delimiters-and-formatting).

None of this replaces the deeper architectural fix — never let injected content trigger real actions without a human or a policy check in between — but it stops the cheap, common attacks before they cost you a model call.

## Output guardrails

Output is where most real damage happens, because output often flows straight into a UI, a database write, or a tool call.

- **Schema validation.** If you asked for structured output, validate it against the schema before using it anywhere. A model that "usually" returns valid JSON will eventually return something that isn't.
- **Content filtering.** Check for things that shouldn't reach the user: leaked system prompt text, PII the model shouldn't be echoing back, or content that violates your own policy — before rendering, not after.
- **Fact and scope checks.** For high-stakes domains (medical, legal, financial), add a verification pass rather than trusting the first answer. See [Guardrails for High-Stakes Output](/learn/hallucinations/guardrails-for-high-stakes-output).
- **Never execute unchecked.** If output feeds a tool call, a SQL query, or a shell command, validate it exactly like you would validate untrusted user input — because functionally, it is untrusted input, generated by a probabilistic process.

## A minimal implementation pattern

You don't need a heavyweight guardrails framework to start. A thin wrapper function around every LLM call does most of the job:

```
function callWithGuardrails(userInput) {
  assertValidInput(userInput);          // length, format, injection heuristics
  const raw = callModel(buildPrompt(userInput));
  const output = parseAndValidate(raw); // schema check, content filter
  if (!output.ok) return fallbackResponse(output.reason);
  return output.data;
}
```

The point isn't the code — it's the habit: every call has an entry check and an exit check, and neither one trusts the model to have done it for you.

## Where guardrails fit in the pipeline

Guardrails are cheap compared to a bad response reaching a user, but they add latency, so budget for them explicitly — see [Setting Latency Budgets for LLM Features](/learn/genai-app-dev/latency-budgets-for-llm-features). And they're not a substitute for testing: run them against your [evaluation suite](/learn/evals-red-teaming/building-a-golden-dataset) so you know what they catch and what still gets through.
