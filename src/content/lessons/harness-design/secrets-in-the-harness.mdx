A harness leaks secrets in three different places at once — the prompt, the persisted transcript, and the telemetry pipeline — and fixing one does nothing for the other two.

## Why the prompt itself is a leak surface

If a tool call pulls a `.env` file, a cloud config, or an API response with an auth header into context so the model can "see what's there," that credential is now inside the conversation. It gets echoed back in the model's reasoning, shows up in any subagent handoff that copies context forward, and rides along if that turn is ever summarized. The fix is to keep secrets out of the token stream entirely: tool implementations read credentials directly from the environment or a secrets manager and never put the value in the string that gets sent to the model — only a reference like `$DATABASE_URL` or a masked `sk-***abcd` should appear in prompts and tool descriptions. This is the same boundary drawn in [Handling API Keys and Secrets Safely](/learn/genai-app-dev/handling-api-keys-and-secrets) for application code; a harness needs it applied one layer earlier, at the tool-call boundary itself.

## Transcripts are logs you didn't mean to write

Every harness that supports session resumption, `--resume`, or crash recovery is writing the full turn history to disk somewhere. That transcript is a durable copy of everything the model saw, including any secret that slipped through despite your prompt-side controls, plus raw tool arguments and outputs that often contain tokens (a curl command with an `Authorization` header, a database connection string in a stack trace). Treat transcript storage the way you'd treat [Redacting PII Before It Hits Your Logs](/learn/production/pii-redaction-in-llm-logs): run a redaction pass on tool inputs/outputs before they're written to the checkpoint file, not after — once a secret is on disk in plaintext, file permissions are your only remaining control, and transcripts routinely get zipped up and shared for debugging.

## Telemetry is the leak nobody checks

Observability spans, error reports, and crash dumps are usually built by serializing whatever object was in scope — which is often the full request payload, headers included. A harness that instruments every model and tool call for tracing needs an explicit deny-list (or better, an allow-list) of which fields are safe to emit as span attributes, applied at the point spans are created, not as a downstream filter that's easy to forget to wire up. This is a policy decision, not a hope: encode it as a redaction function every span-emitting code path is forced to call, in the same spirit as [Guardrails as Code, Not Prose](/learn/harness-design/guardrails-as-code) — a comment telling engineers "don't log secrets" gets bypassed the first time someone adds a debug `console.log` under deadline pressure.

## A concrete pattern: secret references, not secret values

The cleanest fix threads through all three surfaces at once: never let a raw secret value enter the object graph that context, transcripts, and telemetry are all built from.

```text
tool_call: fetch_invoice(account="acme-corp")
  -> resolves API key from vault at call time
  -> key used only inside the HTTP client, in-process
  -> tool result returned to model: {"status": 200, "amount": 4200}
  -> transcript stores: the tool_call and result above, nothing else
  -> span records: tool="fetch_invoice", account="acme-corp", status=200
```

The key exists for the duration of one function call and touches nothing that gets persisted. Everything the model, the transcript, and the tracer see is already secret-free by construction, so there's no redaction step to remember or skip.
