The fastest way to burn through your OpenAI or Anthropic budget isn't a bad prompt — it's a key sitting in your frontend bundle where anyone can scrape it out of dev tools and run it until the bill catches fire. Handling secrets safely is boring, and it's the difference between shipping and getting a $4,000 invoice.

## Never let a key touch the browser

Any environment variable prefixed for client exposure — `NEXT_PUBLIC_`, `VITE_`, `REACT_APP_` — gets bundled into the JavaScript your users download. If your LLM API key lives in one of those, it's public, full stop, regardless of how obscure the bundle looks.

The fix is a server-side proxy: your frontend calls your own backend route, and only that backend holds the real key.

```js
// api/chat.js (server-side only)
export default async function handler(req, res) {
  const response = await fetch("https://api.anthropic.com/v1/messages", {
    method: "POST",
    headers: {
      "x-api-key": process.env.ANTHROPIC_API_KEY, // never sent to the browser
      "content-type": "application/json",
    },
    body: JSON.stringify(req.body),
  });
  const data = await response.json();
  res.status(200).json(data);
}
```

This is also where you enforce your own auth, rate limits, and cost caps before a request ever reaches the provider — see [rate limits and retry strategies](/learn/genai-app-dev/rate-limits-and-retry-strategies) and [cost budgets and usage tracking](/learn/genai-app-dev/cost-budgets-and-usage-tracking).

## Keep secrets out of git

`.env` files are the usual home for local keys, but they're only safe if `.gitignore` actually excludes them — check this on day one of every project, not after a key leaks. Commit a `.env.example` with placeholder values so teammates know what's needed without seeing real credentials.

If a key ever does land in a commit, rotating it is not optional: removing the line in a later commit doesn't remove it from git history. Revoke the old key in your provider dashboard and issue a new one.

## Use a real secret manager in production

`.env` files don't scale past local development. In production, pull keys from a dedicated store instead of baking them into your deploy config:

- **Platform-native**: Vercel/Netlify environment variables, AWS Secrets Manager, Google Secret Manager
- **Dedicated tools**: Doppler, HashiCorp Vault, 1Password Secrets Automation

These give you rotation without a redeploy, per-environment separation (dev vs. staging vs. prod keys), and an audit log of who accessed what. That audit trail matters — it's usually how you first notice a key is being abused, before the bill does.

## Scope keys as narrowly as the provider allows

Where your provider supports it, create separate keys per environment and per service rather than one key shared everywhere. A leaked staging key that can only hit a cheap model does far less damage than a leaked production key with full access. Combine this with the budgets from [setting latency budgets for LLM features](/learn/genai-app-dev/latency-budgets-for-llm-features) and hard spend caps at the provider level as a last line of defense — assume the leak will eventually happen and design so it's cheap when it does.
