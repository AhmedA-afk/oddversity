Constrained decoding can make invalid JSON unreachable. It cannot make wrong values unreachable. That gap is why validation is not optional, not even when you're already using a schema on the request.

## What it is

The validation layer is a single, mandatory checkpoint that sits between "text the model produced" and "an object your code is allowed to act on." Every response passes through it, no exceptions carved out for "the model rarely gets this one wrong" or "we're using strict mode so it's basically guaranteed." It takes raw text in and returns one of exactly two things: a typed, trustworthy object, or a structured error describing precisely what's wrong and where.

This is the same discipline as validating any external input — a form submission, a webhook payload, a query parameter. A model's output is external input. It was generated by a process you don't control, based on a prompt that's one bad edge case away from producing something your code was never built to handle.

## The mental model

Think of it as a customs checkpoint, not a suggestion box. Everything arriving from outside gets inspected before it's allowed past the gate — not because you assume malice, but because "looks fine at a glance" and "verified" are different claims, and only one of them is safe to build on. Nothing downstream — a database write, an API call, a rendered UI — gets to see unvalidated output, ever.

Crucially, the checkpoint's decision is not binary in the way people assume. "Valid" and "invalid" sound like a pass/fail gate, but the useful version of this layer returns three possible outcomes, not two: **accept** the object as-is, **repair** it because the failure looks fixable, or **reject** it because it doesn't belong in an automated pipeline at all. That branching logic is built out in [Validate, Then Branch](/learn/structured-outputs/validate-then-branch-pipeline) — this lesson is about why the checkpoint has to exist unconditionally, before you get to decide what to do with what it finds.

## Why it works this way

Decoding mechanisms and validation solve different problems. [JSON mode](/learn/structured-outputs/json-mode-basics) and [schema-constrained decoding](/learn/structured-outputs/constrained-decoding-under-the-hood) narrow the *space of strings the model can emit* — they can guarantee balanced braces, correct field names, and values that match a type or an enum's literal set. What they cannot narrow is *meaning*. A constrained decoder enforcing an enum of `["pending", "shipped", "delivered"]` will happily emit `"delivered"` for an order that hasn't shipped yet — that's a semantically wrong value sitting inside a perfectly legal string. A required `email` field constrained to be non-empty can still be constrained-decoded into `"none@example.com"` if that's what the model's reasoning produced. The decoder enforced shape; it has no opinion on truth.

This is the same boundary [Structured Output Failure Modes](/learn/structured-outputs/structured-output-failure-modes) draws between structural and semantic failure, and it's why the two need entirely different machinery: a validator built from your schema catches structural breaks — wrong type, missing key, out-of-set enum — mechanically and immediately. It does not, and cannot, catch a value that is well-typed and still false. That second category needs grounding, business-rule checks, or a human, not a stricter parser. [Validation and Auto-Repair](/learn/structured-outputs/validation-and-auto-repair) covers the retry loop this layer feeds into once a failure is found; this lesson is only about the fact that the check runs at all, on every response, unconditionally.

## A concrete example

```python
from pydantic import BaseModel, ValidationError

class Ticket(BaseModel):
    id: str
    priority: int   # 1-5
    status: str     # "open" | "pending" | "resolved"

raw_text = model_response.output_text  # untrusted, always

try:
    ticket = Ticket.model_validate_json(raw_text)
    # ticket is now a typed object — this is the only point
    # in the pipeline where that claim is true
except ValidationError as e:
    for err in e.errors():
        print(err["loc"], err["msg"], err["input"])
    # -> ('priority',) 'Input should be a valid integer' 'high'
```

Nothing before this block should have touched a database, called another API, or rendered anything to a user. The `except` branch isn't a crash path — it's the start of the repair-or-reject decision this whole module is built around.

## Where it shows up

- **API handlers** consuming an LLM-generated response before it becomes a response body or a database row.
- **Tool-call arguments**, validated before the function they name actually executes — see [Tool Schemas](/learn/structured-outputs/tool-function-schemas), where the "arguments" the model hands back are exactly this kind of untrusted input.
- **Extraction pipelines**, validated before a parsed invoice or ticket is written anywhere durable.
- **Streaming consumers**, where the layer runs once, at completion, against the full text — never against a partial buffer (see [Consuming Structured Output as It Streams](/learn/structured-outputs/streaming-structured-output-model)).

## Watch out for

**Testing only your happy-path fixtures.** A validator that's only ever seen three hand-written good examples will look bullproof in a demo and still get surprised by the first real production response with an unexpected null.

**Confusing "it parsed" with "it validated."** `json.loads` succeeding tells you the text is syntactically legal JSON. It says nothing about whether the fields match your schema — that's a second, separate step, and skipping it is one of the most common gaps in a pipeline that otherwise looks careful.

**Validating too late.** If a tool call has already executed, or a row has already been written, by the time validation runs, the checkpoint isn't a checkpoint — it's a postmortem. The layer has to sit strictly before any side effect, not after.
