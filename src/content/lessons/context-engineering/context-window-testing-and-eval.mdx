It's tempting to treat "add more context" as a free win. It isn't. Every extra document, memory, or retrieved chunk you inject is a bet that the model will find and use it correctly — and sometimes that bet loses, quietly, in ways that only show up as a small drop in output quality you'd never catch by eyeballing a few responses.

## Why "it feels better" isn't evidence

A human skimming five outputs before and after a context change will almost always feel more confident with more context present — it looks thorough. But [context rot](/learn/context-engineering/context-rot) means added tokens can dilute attention on the parts that matter, and a model can also get distracted by irrelevant but plausible-looking material. The only way to know which effect wins for your task is to measure it, not read it.

## Set up the ablation

Treat each candidate piece of context as a variable, not a given:

1. Build a fixed eval set of real inputs with known-good outputs or judgeable criteria.
2. Run the task with the context included, and again with it removed — everything else held constant.
3. Score both runs on the same metric: accuracy, a rubric, an [LLM-as-judge](/learn/evals-red-teaming/llm-as-judge) score, or task success rate.
4. Compare. If the "more context" run doesn't beat the baseline outside noise, it isn't earning its place.

This is the same logic as feature ablation in classic ML — you don't know a feature helps until you've tried the model without it. Do this per source of context (one retrieved doc type, one memory category, one tool output) rather than lumping everything into a single before/after, or you won't know which addition is carrying the result and which is dead weight.

## Watch for the failure that hides in the average

A context addition can raise your average score while quietly breaking a subset of cases — for example, helping short queries and actively hurting long ones because it pushes something important out of the window. Slice your eval results by input length, topic, or source count, not just the aggregate. If you're comparing [retrieval vs. stuffing everything in](/learn/context-engineering/retrieval-vs-context-stuffing), this slicing is often where the real answer lives, not in the headline number.

## Make it a gate, not a one-off

The value of a given context source can drift as your prompt, model, or data changes — something that helped six months ago can become dead weight after a model upgrade improves baseline reasoning. Wire this ablation into your existing eval suite so a context change gets the same scrutiny as a prompt change, and re-run it whenever you touch [what gets summarized during compaction](/learn/context-engineering/summarization-for-compaction) or swap a retrieval source. Treat "does this context still earn its tokens" as a question you keep asking, not one you answer once and forget.
