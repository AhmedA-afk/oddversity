[Tracing One Request Through Eight Hops](/learn/genai-app-dev/request-lifecycle-mental-model) named hop 5 — the model generating tokens — as the one that usually dominates total latency. This lesson derives why, mechanically, rather than asking you to take it on faith.

## The request leaves your server

Your server sends an HTTPS POST: a JSON body with the model name, parameters, and message array, over a TLS connection to the provider's endpoint. This part is unremarkable — it's the same kind of request your app makes to any external API, a few kilobytes of text, and on a reasonable connection the transit time for those bytes is small relative to everything that follows. Nothing about the payload being destined for a language model makes this leg special.

## Tokenization

Before the provider's model can process your text, it has to convert it into tokens — the model's actual vocabulary units, which are usually sub-word pieces rather than whole words ("summarization" might become two or three tokens, not one). This step is fast: it's a lookup against a fixed vocabulary, not a model computation, and it happens for both your input and — piece by piece — the model's output as it's produced. The token counts you see in `usage.input_tokens` and `usage.output_tokens` are the direct result of this step, which is why they're an exact count rather than an estimate once the call completes.

## Autoregressive generation: the actual bottleneck

Here's the mechanism that matters most. A language model produces text one token at a time, and — this is the part worth sitting with — **each new token is generated by running the model forward over the entire sequence so far, including every token it has already generated in this response.** Token 1 is produced from your input alone. Token 2 is produced from your input *plus* token 1. Token 50 is produced from your input plus all 49 tokens before it. There is no way to compute token 50 without having already committed to tokens 1 through 49 — the process is fundamentally sequential, not parallelizable across the length of a single response.

This is the mechanical reason a longer response takes meaningfully longer to produce than a short one, independent of network conditions entirely: it isn't "more data to transfer," it's "more sequential forward passes, each one waiting on the last." Doubling the expected output length roughly doubles the number of these sequential steps, which is a very different cost than doubling a file size you're downloading over a fast connection.

Contrast this with tokenizing your *input*: the provider can process your entire prompt in parallel in one pass, because none of those tokens depend on ones the model itself is about to generate. That asymmetry — parallel over the input, strictly sequential over the output — is why response length affects latency far more than input length does, for a fixed total token count.

## Time-to-first-token vs. total time

These are two different numbers, and conflating them is the single most common mistake in reasoning about GenAI latency:

- **Time-to-first-token (TTFT):** how long from sending the request until the *first* output token is ready. This covers everything before generation starts producing usable output — network transit to the provider, tokenizing the input, and running the initial forward pass.
- **Total time:** how long until the *entire* response is finished — TTFT, plus every sequential generation step after the first token, plus the final leg of transit back to you.

A non-streaming call only ever reports total time to your code — you wait for everything, then get it all at once. [Streaming](/learn/genai-app-dev/streaming-responses-to-the-ui) exposes TTFT directly, because you start receiving (and can start rendering) tokens the moment the first one is ready, rather than waiting for the last one. This is why streaming improves the *felt* experience of a slow response without changing its actual total generation time at all: it moves the moment the user sees something from "total time" to "TTFT," but the model still needs the same number of sequential steps to finish the rest.

## Where "tokens per second" comes from

A provider's or a model's throughput is typically expressed as output tokens per second — the inverse of "how long does one sequential generation step take, on average, for this model on this hardware." If you know a response's total output token count and its total generation time (excluding transit and TTFT), you can back into this rate yourself:

```text
tokens_per_second = output_tokens / generation_time_seconds
```

For example, if a response carrying 200 output tokens took 8 seconds of generation time after the first token arrived, that's an effective rate of `200 / 8 = 25` tokens per second for *that specific call* — illustrative arithmetic, not a claim about any particular model or provider's real throughput, which varies by model size, hardware, current load, and provider, and which you should measure for your own calls rather than assume from a number you read somewhere. The mechanism this lesson exists to establish is *why* this number is roughly constant per token regardless of response length (each step does comparable work) rather than what the number's actual value is for any given system.

## What this explains

Once generation is understood as strictly sequential per response, several things that otherwise look surprising stop being surprising:

- Why `max_tokens` set far higher than you need doesn't cost you anything *if the model stops naturally* — the cost is per token actually generated, not per token allowed.
- Why two calls with identical input length but different expected output length (a one-line classification versus an open-ended draft) have very different latency profiles, even on the same model and provider.
- Why batching multiple independent generations into one enormous response is usually worse for perceived latency than making separate calls you can stream and render independently — see [Latency Budgets for LLM Features](/learn/genai-app-dev/latency-budgets-for-llm-features) for the applied version of that tradeoff.

None of this requires knowing a provider's internal architecture. It falls directly out of one fact: generating token *N* requires having already generated token *N−1*.
